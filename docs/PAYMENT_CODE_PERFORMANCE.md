# 校园付款码弱网验证与优化方案

## 当前行为与边界

每次打开付款码都会新建 `SchoolWebActivity` 和 WebView，加载学校官方 `https://ecard.sit.edu.cn/epay/h5/v5qrcode`。退出后销毁 WebView；Cookie 与学校网页存储按现有机制保留。应用没有独立的本地生码能力，也未确认学校码的有效期或离线校验协议。

测试只打开页面，不扫码、不扣款、不保存码图、不读取或输出码内容、账号、票据、Cookie 或页面快照。有效码出现和真实食堂环境的结论，必须由账号持有人在现场补验。

## 测量方法

使用单独的测试签名包及测试模拟器，登录由账号持有人自行完成；不要替换正式签名安装，不要清除他人的账号数据。

运行 `tests/android/PaymentCodeTimingInstrumentation.java`：

```text
adb -s <测试设备> shell am instrument -w cn.xinxinxiangying.app.test/.PaymentCodeTimingInstrumentation
```

输出仅包含状态和两个时长：`pageReadyMs`（官方页面文档完成）、`graphicCandidateMs`（二维码容器中出现可见 canvas/img）。负数表示未观测到；30 秒结束。检测依赖容器命名包含 qrcode，需在真实页面确认选择器后使用。可见图形可能为空画布或旧码，因此这个探针不能单独证明码已可用；未识别不能推断学校未出码。

人工另记从点击入口到新鲜有效码出现的时间；若只有加载动画、过期码、错误提示或登录页，均判为未出码。每组至少 10 次，分别统计首次/再次打开的中位数、P95 和超时次数；样本过少时列原始时长，不报 P95。

| 场景 | 建议条件 | 核对重点 |
| --- | --- | --- |
| 正常网络 | 不限速，无额外延迟 | 冷启动与再次打开基线 |
| 弱网 | 下载 256 kbps，上行 128 kbps，额外延迟约 800 ms | 资源加载与码接口分别耗时 |
| 高延迟 | 下载 1 Mbps，额外延迟约 1500 ms | 是否反复跳转或重登 |
| 丢包 | 用支持丢包的网络工具设为 5% | 重试、超时与恢复；模拟器限速不能替代丢包模拟 |
| 断网/恢复 | 打开前断网，之后恢复 | 不把旧画面标为有效码 |
| 会话过期 | 在独立测试账号上完成 | 提示重新登录，不无限等待 |
| 食堂现场 | 本人手机、实际高峰网络 | 人工确认有效期与扫码兼容性，支付由本人操作 |

模拟器限速仅用于指定测试设备，测完恢复原设置；不要修改电脑全局代理或校园网络。真机弱网还包括信号切换、干扰、DNS 和网关拥塞，模拟结果不能代替现场结果。

## 优化顺序

1. 先确认时间花在 WebView 启动、SSO、静态资源还是码接口，避免只测页面加载条。
2. 若静态资源占主导，先核对校方缓存头和正常 WebView 缓存命中情况；不强制缓存动态码、认证响应或过期内容。
3. 若 WebView 重建占主导，评估前台短时复用页面；切换账号、退出或过期时必须销毁。回到付款码页面需确认官方刷新机制，不能仅显示旧截图。
4. 若校方支持明确的码有效期与主动刷新，可评估仅在用户前台打开工具页时提前加载；先说明额外请求和会话处理方案，再开发验证。不持续后台轮询。
5. 若码接口本身受网络限制，提供明确的加载、失败、重试状态；只有学校公开支持离线码协议时才考虑离线能力。

当前不改付款码产品逻辑。优先讨论目标：已登录且网络可用时，再次打开争取 2 秒内、冷启动争取 5 秒内；这是待验证的体验目标，不是性能承诺。离线截图、无限延长码有效期和自行猜测生码算法不列为优化方案。

## 2026-10-24 本机验证记录

- 原生 SDK 构建、测试 APK 签名和对齐通过。
- 独立合成设备正确返回 `login-required`。已有账号的设备起初返回 `school-login-required`；账号持有人随后自行重新登录并确认已出码。
- 在相同模拟器、相同会话下，以固定顺序各测 3 次新建 WebView 到候选图形可见。没有清空缓存，不读取码内容或校验码有效期，没有执行支付。
- 模拟器 37 的 console 限速不覆盖默认 Wi-Fi 路径，因此测量时暂时关闭该测试设备的 Wi-Fi，并确认活动网络为蜂窝模拟链路；测试结束已恢复不限速、无额外延迟以及原来的 Wi-Fi/移动数据状态。方法依据 [Android 官方模拟器 console 文档](https://developer.android.com/studio/run/emulator-console)。没有修改电脑全局网络。

| 网络条件 | 三次观测（秒） | 中位数（秒） |
| --- | --- | --- |
| 不限速、无额外延迟 | 9.216 / 13.071 / 10.911 | 10.911 |
| 上行128、下行256 kbps；额外延迟800 ms | 13.827 / 9.852 / 16.333 | 13.827 |
| 双向1024 kbps；额外延迟1500 ms | 7.968 / 7.316 / 7.139 | 7.316 |

9 次均检测到官方码页面的候选图形，文档完成和候选图形首次观测在同一轮轮询，观测粒度约 200 ms 加回调耗时。这些时长包括 WebView 初始化和网页加载，不含用户手动扫码验证。高延迟组反而较快，可能混有预热、缓存及校方服务波动，当前数据不能分离原因；仅 3 个样本，不报 P95、不声称达到性能目标。

结论：现有新建页面流程存在数秒等待，优先补测 WebView 初始化、认证跳转、静态资源与码请求各阶段。随后再决定是否做前台短时复用和官方刷新；当前不根据这组数据直接缓存动态码或新增预加载。真实食堂网络、丢包、断网恢复、码刷新与有效期以及真机扫码兼容性仍待验收。
